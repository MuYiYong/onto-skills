# finance-domain-knowledge

## 定位与解决的问题

建立金融业务共同词汇，避免把产品、合同、交易、账户和主体角色混为一类。

## 适用与不适用

用于上述金融行业知识与建模任务。只处理请求范围，不能将项目解释当成标准原意；不负责 GQL 语法、生产数据操作或自动作出不利业务决定。

## 输入

金融业务描述、地区/时期、数据字典或流程；可选给出标准版本。没有来源的行业说法先标待核实。

## 工作流程

1. 读取 [术语与边界](references/glossary.json) 和 [来源索引](references/sources.json)，只选与当前业务相关概念。
2. 识别参与主体、金融产品类型、具体合同、账户、交易及结算过程；将债权/债务视角与底层义务安排对齐。
3. 区分授信额度/决定、已签合同、实际放款、余额快照和还款；明确金额、币种及时间口径。
4. 提取业务关系与规则，记录角色、生命周期和例外；按 [方法](references/method.md) 进行取舍。
5. 逐项注明项目整理、行业通用、标准原意或建模推断，必要时再核实用户指定标准。
6. 输出金融概念和关系表、业务问题与知识缺口；若需图模型，可直接按身份和关系意义给出中立设计建议。

## 输出

金融术语表、业务角色/概念/关系表、流程与规则、来源与适用范围、歧义及待确认项。

## 资源

先读 [方法](references/method.md)，按流程读取所需 JSON，需演示时读 [工作示例](examples/worked-example.md)。来源和基本知识随本 Skill 分发；仅在用户要求最新标准或缺少必要原文时再检索，离线可使用给定材料并明确缺口。

## 质量检查与约束

核对术语、身份范围、角色、时间和来源；保留标准/通用/整理/推断的分类。未知阈值不杜撰，示例阈值不推广为监管要求。单独安装可完成本职工作；其他 Core、Finance 或 Scenario 技能是可选组合。

## 示例

业务说“客户拥有产品余额”：需澄清产品是类别还是具体账户/合同。输出 ProductDefinition、Contract/Account、BalanceObservation 三层候选，余额带 as_of/currency，而不是直接在产品类别上存客户余额。
