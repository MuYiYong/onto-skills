# ontology-documentation

## 定位与解决的问题

生成与模型一致、可追溯、可交接的本体设计文档。

## 适用与不适用

在用户请求上述建模工作时使用。仅加载与当前问题相关的材料；不强制调用其他 Skill。不用于具体行业标准定义的替代、GQL 语法生成或未经授权的数据库操作。

## 输入

当前模型版本、需求/业务问题、来源、映射与验证结果；缺少字段可标待补，不能无依据补成已确认。

## 工作流程

1. 记录文档对应的 model_id/version、适用业务、排除项、目标环境及审查状态。
2. 使用 [文档模板](references/method.md) 整理术语、概念、身份、生命周期、属性和关系目录。
3. 展示概念层次与关系方向；图示只是辅助，仍保留可检索的文字规格。
4. 将来源版本、标准 IRI、业务扩展、映射损失、约束与执行位置串联。
5. 把业务问题的输入/预期答案和验收证据列入文档；分别记录静态/推理/数据库结果。
6. 记录未决事项、变更影响及领域确认；有 GQL 交接时记录外部版本与回传语义审查，不内嵌维护语法指南。
7. 核对所有名称、字段、端点和基数与当前规格一致，标注最终交付状态。

## 输出

带版本的本体设计文档：范围、术语、概念、图结构、约束、映射/损失、来源、业务问题、质量报告、开放问题和变更历史。

## 资源

开始工作时读 [方法与决策](references/method.md)，需要完整演示时读 [示例](examples/worked-example.md)。资源均随本 Skill 分发；外链仅用于来源核实，不是基本功能的在线依赖。

## 质量检查与约束

用业务正反例检验输出是否覆盖需求、身份和来源。明确区分已知事实、项目方法和模型推断；缺少证据的结论标待确认。用户明确要求优先于本技能建议。静态模型审查不能冒充领域专家确认、OWL 推理或数据库原生运行结果。

需要组合时把本次输出作为下一步输入；其他技能是可选增强，基本流程独立可执行。

## 示例

用户给出的 Equipment 模型 v0.2 主键是 asset_id，旧设计文档使用 serial。以 v0.2 规格生成目录并将旧 serial 说明移入变更记录，不能沿用错误主键。
