# ontology-evolution

## 定位与解决的问题

提供可追溯的语义差异和可验证的演进计划。

## 适用与不适用

在用户请求上述建模工作时使用。仅加载与当前问题相关的材料；不强制调用其他 Skill。不用于具体行业标准定义的替代、GQL 语法生成或未经授权的数据库操作。

## 输入

旧/新模型、业务问题、数据消费者、标准版本与迁移约束；缺少旧版时先建立基线，不假造历史差异。

## 工作流程

1. 固定旧/新版本及各自来源，先按稳定概念 ID/IRI 对齐，再看名称；改名不自动视为删除加新增。
2. 按 [变更判定](references/method.md) 比较概念、键、属性类型/空值/多值、关系方向/基数/时效和约束。
3. 对上游标准升级检查 IRI 重命名、定义/限制变化、弃用及 imports 闭包；记录与业务扩展的冲突。
4. 分开评估语义、数据、查询/API 和实现兼容；新增字段也可能改变数据完整性要求。
5. 设计转换、回填、双读/过渡、去重与回滚步骤；标出不可逆转换和需用户决定的映射。
6. 形成回归业务问题与正反样例：键碰撞、端点缺失、时效重叠、缺失新必填值和旧消费者兼容。
7. 输出差异、风险、版本建议与验收门槛；任何实际迁移需用户明确授权，保持原模型及证据可追溯。

## 输出

版本差异表；概念/字段映射；分维度兼容矩阵；消费者影响；迁移/回滚计划；待确认事项；回归用例及发布门槛。

## 资源

开始工作时读 [方法与决策](references/method.md)，需要完整演示时读 [示例](examples/worked-example.md)。资源均随本 Skill 分发；外链仅用于来源核实，不是基本功能的在线依赖。

## 质量检查与约束

用业务正反例检验输出是否覆盖需求、身份和来源。明确区分已知事实、项目方法和模型推断；缺少证据的结论标待确认。用户明确要求优先于本技能建议。静态模型审查不能冒充领域专家确认、OWL 推理或数据库原生运行结果。

需要组合时把本次输出作为下一步输入；其他技能是可选增强，基本流程独立可执行。

## 示例

Equipment v1 以 serial 标识，v2 以 (source_system, asset_id) 标识。即使所有字段名未变也属身份语义变化；先列碰撞和边重连映射，再设计验证与回滚，不能直接覆盖键。
