# entity-relationship-modeling

## 定位与解决的问题

把概念模型细化成可映射到图的实体与关系规格。

## 适用与不适用

在用户请求上述建模工作时使用。仅加载与当前问题相关的材料；不强制调用其他 Skill。不用于具体行业标准定义的替代、GQL 语法生成或未经授权的数据库操作。

## 输入

概念/业务描述、数据字段、典型记录与业务问题；至少明确实体身份的候选来源。可在没有前置 Skill 时直接从业务材料开始。

## 工作流程

1. 列候选实体并记录稳定身份、命名空间和生命周期；将可推导且无关系意义的值优先留作属性。
2. 为主键记录复合字段、空值策略、跨源去重和键变更策略；来源系统编码只在其命名空间内唯一。
3. 每个动词关系明确 source → target、反向解读、每端最小/最大基数、是否有重复发生。
4. 检查关系上的金额、角色和时间；二元关系可用带属性边，多方/独立生命周期关系用关联实体。
5. 明确多重边身份；重复两次交接不能因为端点相同就丢失第二次。
6. 把 valid time、记录时间和事件时间分开；空结束时间表示尚未结束还是未知，需要业务定义。
7. 以 [关系审查表](references/method.md) 复核；以反例记录检验键碰撞、孤立端点与基数例外。

## 输出

实体表（身份/属性/来源）；关系表（端点/方向/每端基数/关系属性/多重边键/时效）；关联实体取舍说明；反例和未知事项。

## 质量检查与约束

用业务正反例检验输出是否覆盖需求、身份和来源。明确区分已知事实、项目方法和模型推断；缺少证据的结论标待确认。用户明确要求优先于本技能建议。静态模型审查不能冒充领域专家确认、OWL 推理或数据库原生运行结果。

需要组合时把本次输出作为下一步输入；其他技能是可选增强，基本流程独立可执行。

## 示例

Employee → Department 的 ASSIGNED_TO 在某时刻每员工 0..1 部门，但历史可有多条。边用 assignment_id 区分调岗，valid_from/valid_to 记录任职区间。部门名称和员工姓名都不是主键。
